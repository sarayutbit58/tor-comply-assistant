# ข้อกำหนดที่ยืนยันแล้ว — TOR Comply Assistant

ปรับปรุง: 2026-09-30 (Asia/Bangkok) จากการหารือกับผู้ใช้ในวันที่ 2026-09-29

ไฟล์นี้เป็นข้อกำหนดผลิตภัณฑ์ที่ตกลงกันแล้ว สภาพ implementation และข้อจำกัดปัจจุบันอยู่ใน [CONTEXT.md](../CONTEXT.md) ส่วนผลตรวจในอดีตอยู่ใน [รายงาน QA](qa-2026-09-29.md) คำสั่งใหม่โดยตรงจากผู้ใช้มีผลเหนือข้อสรุปเดิม

## 1. เป้าหมายและขอบเขต

ช่วย Presales ทำ Comply TOR ราชการไทย ตั้งแต่นำเข้าข้อกำหนด เลือกสินค้า/บริการ ค้นและจัดหลักฐาน ไฮไลต์พร้อมเลขข้อ ไปจนถึงส่งออกตาราง เพื่อลดเวลาอ่านเทียบเอกสารและจัดตาราง

| ประเด็น | การตัดสินใจ |
|---|---|
| อุปกรณ์ | โน้ตบุ๊กเท่านั้น; ข้อกำหนดรองรับโทรศัพท์ถูกยกเลิกโดยผู้ใช้ |
| การเก็บงาน | ในเบราว์เซอร์เครื่องที่ใช้งาน ไม่มีการซิงก์ข้ามเครื่อง |
| แหล่งสินค้า/หลักฐาน | ไฟล์ที่ Presales อัปโหลดในแต่ละโครงการ |
| ไฟล์เริ่มโครงการ | ตาราง Comply ไฟล์เดียวเป็นทั้งแหล่งข้อกำหนดและแม่แบบ; ช่องคำตอบจะว่างหรือกรอกแล้วก็ได้ |
| การย้ายงาน | ส่งออก/นำเข้าไฟล์โครงการหนึ่งไฟล์ที่รวมต้นฉบับและสถานะทั้งหมด |
| AI | รอบปัจจุบันใช้กฎในโค้ดก่อน; เปิด AI ภายหลังเมื่อผู้ใช้ขอ |
| ธีม | ใช้ CI ของ 1TOALL จากทรัพยากรแบรนด์ที่เตรียมไว้ |

ลำดับกฎเฉพาะงาน: **Internet → Network → Server → CCTV → Security** หมวดอื่นอยู่ในขอบเขตงานที่ผู้ใช้ทำ แต่เกิดไม่บ่อย ได้แก่ IT, Software, Surveillance system, Parking system, ระบบจองห้องประชุม, Access Control, A/V และ PBX/IPBX/Hybrid

## 2. หน้าทำงานและการนำทาง

- เห็นตาราง Comply, TOR ต้นฉบับ และเอกสารหลักฐานพร้อมกัน; ตารางอยู่ในหน้าทำงานตลอดช่วงทำ Comply
- ปรับความกว้างแต่ละช่องได้ มีเครื่องมือจัดการไฟล์ ข้อ TOR แม่แบบ และตั้งค่าโครงการ
- เมื่อเลือกแถว TOR ให้ช่องต้นฉบับเปิดหน้าของข้อนั้น และช่องหลักฐานเปิดจุดแรกที่ผูกไว้
- หากมีหลายจุด ให้มีรายการจุดอ้างอิงสำหรับกดเปิดจุดอื่น
- หากยังไม่มีหลักฐาน แสดง **“ยังไม่ผูกหลักฐาน”** และเปิดทางให้เลือกเอกสารเพื่อเพิ่มจุดอ้างอิง
- การเปิดหน้าเอกสารเป็นการนำทาง ไม่ใช่หลักฐานว่าข้อนั้น Comply แล้ว

## 3. ประเภทไฟล์และการจัดกลุ่ม

Presales ต้องกำหนดบทบาทไฟล์ก่อนใช้ ระบบแยก TOR, หลักฐานสินค้า, หลักฐานบริการ, หลักฐานคุณสมบัติผู้ยื่นข้อเสนอ และแม่แบบตาราง Comply

**ไฟล์ TOR และตาราง Comply ไม่มีสิทธิ์เป็นหลักฐาน:** ข้อความ TOR, คำตอบเดิม และผล Comply เดิมจะไม่ถูกใช้ยืนยันตัวเอง ตารางที่นำเข้าเป็นไฟล์เริ่มโครงการอ่านเฉพาะหัวคอลัมน์ เลขข้อ และข้อกำหนด พร้อมเก็บรูปแบบเป็นแม่แบบ ช่องรายละเอียดที่เสนอ ผล และอ้างอิงเริ่มใหม่ทั้งหมด ส่วนการอัปโหลดเป็นแม่แบบอย่างเดียวภายในโครงการยังใช้เฉพาะรูปแบบ

ก่อนสร้างโครงการให้มี preview และยืนยันคอลัมน์เลขข้อ/ข้อกำหนด รองรับ DOCX, XLSX และ PDF ที่อ่านข้อความได้ ไม่สมมติว่าคอลัมน์สองช่องแรกต้องเป็นเลขข้อและ TOR เสมอ ถ้ามีหลายตารางให้เลือกกลุ่มที่ใช้หัวคอลัมน์เดียวกัน ตาราง Comply ที่ไม่ได้เลือกต้องไม่พาคำตอบเก่าติดไปในผลส่งออก

สินค้าและบริการเป็นรายการคนละชนิด:

| ชนิด | ข้อมูลที่ Presales จัดเตรียม |
|---|---|
| สินค้า | ชื่อ ยี่ห้อ รุ่น และไฟล์ที่ยืนยันสินค้านั้น |
| บริการ | ชื่อบริการ ผู้ให้บริการ และรายละเอียดตามงาน เช่น จุดต้นทาง–ปลายทาง ความเร็ว หรือหนังสือรับประกัน |

ใช้ไฟล์ของโครงการนั้น; ยังไม่มีคลังกลางหรือการค้นเว็บผู้ผลิตอัตโนมัติ Presales ระบุ metadata และจัดไฟล์เอง

## 4. การเสนอและเลือกสินค้า/บริการ

- ระบบเสนอรายการที่อาจตรง TOR พร้อมข้อมูลที่ตรวจได้จากไฟล์ แต่ Presales เป็นผู้เลือกก่อนเริ่ม Comply
- เลือกเป็น **รายข้อ TOR**; หนึ่งข้อเลือกสินค้า/บริการได้หลายรายการ
- รายการที่เลือกหลายรายการหมายถึง **ต้องใช้ร่วมกัน** ไม่ใช่ตัวเลือกทดแทนกัน
- ตรวจว่าแต่ละรายการตอบเงื่อนไขส่วนใด และรวมหลักฐานให้ครบทั้งข้อ
- ข้อคุณสมบัติผู้ยื่นข้อเสนอใช้หลักฐานบริษัทตามประเภทข้อ; ไม่ต้องสร้างสินค้า/บริการสมมติเพื่อให้เลือกได้

## 5. หลักฐานและเครื่องหมาย

- TOR หนึ่งข้อผูกได้หลายจุด ทั้งในเอกสารเดียวและข้ามไฟล์
- หลักฐานหนึ่งจุดผูกได้หลายข้อ โดยเก็บเครื่องหมายเดียวและรวมเลขข้อ เช่น **“ข้อ 5.1, 5.2”**
- ยกเลิกการผูกกับข้อหนึ่งได้โดยจุดเดิมยังเป็นหลักฐานของข้ออื่น
- เก็บไฟล์ หน้า PDF จริง เลขหน้าที่พิมพ์ (ถ้ามี) พิกัดกรอบ และข้อความที่อ้าง เพื่อย้อนตรวจได้
- เอกสารที่ผู้เสนอราคาจัดทำเอง เช่น เอกสารเทคนิค หนังสือรับประกัน หรือแผนผัง ใช้เป็นหลักฐานได้ตามกฎการเทียบ ผู้ใช้ไม่ได้ขอให้ระบบจัดชั้นผู้ออกเอกสารเป็นเกณฑ์ผ่าน/ไม่ผ่าน
- ผลการเทียบยืนยันความสอดคล้องกับเอกสารที่อัปโหลด ไม่ใช่การตรวจความแท้จริงของเอกสารหรือรับรองการส่งมอบจริง

## 6. โหมดและกฎการตัดสิน

เลือกโหมดหลักระดับโครงการ และเปลี่ยนเฉพาะข้อได้:

| โหมด | พฤติกรรม |
|---|---|
| ตรวจยืนยันเอง | ระบบเสนอหลักฐาน/เหตุผล; Presales ตัดสินผล |
| Auto ตามกฎ | โค้ดตัดสินเมื่อเงื่อนไขที่รองรับและหลักฐานครบ; ข้อที่ยังพิสูจน์ไม่ได้เป็นรอตรวจ |

เกณฑ์ที่ตกลง:

1. เงื่อนไขสาระสำคัญตาม TOR ต้องมีหลักฐานครบทุกส่วน คำเรียงสลับกันได้โดยไม่เปลี่ยนความหมาย
2. แยกกฎจำนวนขั้นต่ำ/สูงสุดออกจากกฎคุณสมบัติที่ต้องตรง และแยกหน่วย/มิติให้ถูกต้อง
3. **24 พอร์ตขั้นต่ำ → 48 พอร์ต** ผ่านกฎจำนวนได้ แต่ **25G อย่างเดียวไม่ยืนยันว่ารองรับ 10G** ต้องมีข้อความหรือรายการความเร็วที่ยืนยันจริง เช่น 100/1000/10000/25000 Mbps
4. คำปฏิเสธ เช่น “ไม่รองรับ” หรือ “unsupported”, บิต/ไบต์, ขอบเขตตัวเลข, เวอร์ชันมาตรฐาน และเงื่อนไข optional ต้องไม่หายไปในการ normalization
5. ข้อความตรงหรือคะแนนคำค้นเพียงอย่างเดียวไม่ใช่ผล Comply; ใช้เงื่อนไขในกฎและรายการที่ Presales เลือก
6. ค่าหรือความสามารถที่ระบุชัดว่าไม่ผ่านเกณฑ์เป็น **ไม่ Comply**; ขาดหลักฐาน ข้อมูลขัดแย้ง หรือยังแยกเงื่อนไขไม่ได้เป็น **รอตรวจ**
7. ผล **Comply** ต้องมีรายละเอียดที่เสนอ พร้อมหลักฐานรองรับครบตามสินค้า/บริการที่ใช้ร่วมกัน
8. แสดงเหตุผลและสิ่งที่ยังพิสูจน์ไม่ได้ให้ Presales ตรวจย้อนหลังได้

วันที่ 2026-09-30 ผู้ใช้อนุมัติช่วงทดสอบ API: OpenAI สำหรับ LLM/OCR และ TypeSafe สำหรับ System One ตาม session 01a0f0d7-4994-7c12-b65b-b46a432de5b7 ใช้คีย์ที่ผู้ใช้กรอกสำหรับแท็บนั้นเท่านั้น โดยค่าใช้จ่ายเป็นของบัญชีผู้ใช้ ส่งเฉพาะ TOR ข้อปัจจุบันและข้อความ/ภาพที่เลือกหลังเปิดอนุญาต AI เป็นผู้เสนอผล; โค้ดและ Presales ยังคุมกฎและการยืนยัน

คีย์เข้ารหัสในหน่วยความจำ ไม่เก็บลง Cookies, Cache, local/session storage, IndexedDB หรือไฟล์โครงการ ปิดแท็บ/รีโหลดต้องกรอกใหม่ ดึงรายชื่อโมเดลใหม่ทุกครั้งที่ส่งคีย์ แนะนำ OpenAI สูงสุด 5 ตัวที่บัญชีใช้เรียกรายการได้ แบ่งง่าย/กลาง/ยากและเริ่มงานง่าย; TypeSafe แสดง Jev stable โดยไม่มีตัวเลือกเปลี่ยน การดึงโมเดลไม่ได้ยืนยัน quota inference การเข้ารหัสไม่ได้ป้องกัน XSS/ส่วนขยายอันตรายทั้งหมด

ผู้ใช้เพิ่ม OpenRouter สำหรับ LLM/OCR ในวันที่ 2026-09-30 เลือกผู้ให้บริการสองงานแยกกันได้ คีย์ OpenRouter ใช้กฎชั่วคราวเดียวกัน ตรวจคีย์ผ่าน endpoint เฉพาะคีย์ก่อนดึง catalogue ใหม่ OCR ใช้เฉพาะโมเดลรับภาพ และร่างคำตอบใช้เฉพาะโมเดล structured output ที่รองรับ ไม่มีการสลับไปโมเดลอื่นเมื่อผิดพลาด และคงกฎ/หลักฐาน/การตรวจของ Presales เดิม

## 7. OCR และการตรวจโดยคน

การเปลี่ยนแปลงวันที่ 2026-09-30 **ยังไม่เพิ่มระบบ OCR** สำหรับการนำเข้าตาราง: รอบนี้ใช้ DOCX/XLSX หรือ PDF ที่มีข้อความให้อ่าน หากเป็นไฟล์สแกนให้แจ้งข้อจำกัดและขอไฟล์ที่อ่านข้อความได้ ความสามารถ OCR ของขั้นตอนเดิมเป็นคนละขอบเขต

การอนุมัติ API ในวันเดียวกันเปลี่ยน recognizer ของ OCR หน้า TOR/กรอบหลักฐานเป็น OpenAI vision หลังเชื่อมคีย์ ไม่เพิ่มการเดาเส้นตารางหรือพิกัดจาก LLM; ตำแหน่งใช้หน้าจริงและกรอบที่โค้ดเก็บ ต้องตรวจเทียบภาพและคง review gates เดิม

- Presales ตรวจเทียบข้อความ TOR ที่อ่านได้ก่อนเสมอ โดยเฉพาะเลขข้อ คำปฏิเสธ ตัวเลข หน่วย และเงื่อนไข
- ต้องยืนยัน TOR ครบทุกข้อและทุกหน้าที่ต้อง OCR ก่อนใช้ Auto ทั้งรายข้อและทั้งโครงการ
- สำหรับหลักฐานสแกน Presales ตรวจเฉพาะข้อความที่ระบบนำมาอ้าง/ไฮไลต์ ไม่ต้องตรวจ OCR ทุกหน้า
- ข้อความหลักฐาน OCR ที่ถูกอ้างต้องตรวจเทียบภาพก่อนยืนยันผ่านหรือส่งออก
- เก็บ page identity ของงาน OCR ขณะเริ่มอ่าน; การเปลี่ยนหน้าบน UI ต้องไม่ทำให้ผลไปผูกผิดหน้า

## 8. แม่แบบและผลส่งออก

หนึ่งโครงการใช้แม่แบบไฟล์เดียว อาจเป็น **DOCX, PDF หรือ XLSX** แล้วสร้างผลส่งออกได้ทั้ง **PDF, DOCX และ Excel**

- ไฟล์เริ่มโครงการใช้ข้อ TOR กับรูปแบบจากตารางเดียวกัน; แม่แบบอย่างเดียวใช้รูปแบบเท่านั้น ทั้งสองกรณีไม่อ่านคำตอบ/สถานะเดิมมาใช้ต่อ
- คงหน้าตาเดิมให้ใกล้ที่สุด รวมถึงหัวคอลัมน์ สี เส้น และองค์ประกอบของหน้า โดยมี preview และการจับคู่คอลัมน์ให้ตรวจ
- DOCX ที่ใช้แม่แบบ DOCX คงโครงสร้างตารางและหัว–ท้ายหน้าที่รองรับ รวมถึงแถวหัวเรื่องก่อนหัวตาราง
- PDF/DOCX ที่แปลงข้ามชนิดไฟล์อาจจัดหน้าใหม่; ความเหมือนแบบ pixel-perfect ทุกชนิดไม่ได้เป็นสิ่งที่รับประกัน
- Excel ต้องแก้ไขและกรองสะดวก พร้อมคงสไตล์หลักของแม่แบบ แถวข้อมูลไม่ถูกทำเป็นกลุ่มเซลล์รวมเพื่อจำลองหน้ากระดาษ
- ข้อมูลตารางหลักคือรายละเอียด TOR, รายละเอียดที่เสนอ, ผลเปรียบเทียบ และเอกสารอ้างอิงไฟล์/หน้า อาจมีคอลัมน์เลขข้อแยกตามแม่แบบ
- ส่งออกสำเนา PDF หลักฐานที่มีไฮไลต์และเลขข้อร่วม โดยเก็บต้นฉบับไว้
- ผลรอตรวจต้องยังแสดงว่าเป็นรอตรวจ ไม่ถูกเปลี่ยนเป็นผ่านเพื่อให้ส่งออกได้

## 9. ไฟล์โครงการสำหรับสำรองและย้ายงาน

ไฟล์เดียวต้องรวม TOR, เอกสารหลักฐานทั้งหมด, แม่แบบ, การจัดกลุ่มสินค้า/บริการ, ไฮไลต์, คำตอบ, เหตุผล และสถานะตรวจ เพื่อเปิดทำต่อบนอีกเครื่องโดยไม่ตามหาไฟล์แนบเดิม

การนำเข้าต้องรักษาการผูกหลายข้อ/หลายรายการ ตรวจความครบและการอ้างอิง แล้วสร้างโครงการแยกจากเดิม ห้ามเขียนทับโครงการที่มีอยู่โดยไม่ตั้งใจ

ไฟล์ที่ใช้เป็นต้นฉบับและแม่แบบพร้อมกันต้องถูกเก็บ/สำรองเพียงครั้งเดียว และการเปลี่ยนแม่แบบภายหลังต้องไม่ลบต้นฉบับที่โครงการยังอ้างอยู่

## 10. หลักฐานรับงาน

ใช้เอกสารสังเคราะห์ตรวจเส้นทางที่เปลี่ยน โดยเลือกตามผลกระทบ: review gates, การจัดประเภทไฟล์, กฎผิดหน่วย/คำปฏิเสธ/ขีดความสามารถ, หลายรายการใช้ร่วมกัน, หลักฐานร่วม, OCR ผิดหน้า, รูปแบบแม่แบบ, ผลส่งออกจริง และการย้ายโครงการกลับเข้า

บันทึกสิ่งที่ทดสอบ revision/สภาพแวดล้อม ผลที่เห็น และส่วนที่ยังไม่ได้ทดสอบ แยกผลตรวจในอดีตออกจากผลตรวจของการเปลี่ยนแปลงครั้งใหม่
